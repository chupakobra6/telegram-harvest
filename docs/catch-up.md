# Catch-up в Telegram Harvest

Этот файл — канонический контекст для запросов «сделай catch-up» или «сделай катчап». Перед таким прогоном агент должен прочитать его и не восстанавливать смысл команды по старым чатам.

## Catch-up без уточнений

По умолчанию catch-up означает **daily catch-up основного личного аккаунта**:

- профиль: `main`;
- данные: только исходящие/self-сообщения владельца аккаунта во всех доступных диалогах;
- период: день после самого свежего `reports/daily/YYYY-MM-DD.md` по вчерашний день включительно;
- сегодняшний незавершённый день не входит;
- существующие отчёты не переписываются;
- результат для человека: отдельный Markdown за каждый день в `reports/daily`;
- JSONL, ASR-логи, кэши и временные данные остаются в `.state/daily` и не являются пользовательскими отчётами.

Штатная команда:

```bash
make daily-catchup PROFILE=main PROGRESS=1
```

Если предыдущих daily-отчётов нет, начальная дата должна быть задана явно:

```bash
make daily-catchup PROFILE=main FROM=2026-07-01 PROGRESS=1
```

Нельзя выбирать профиль неявно. `main` и `study` — конфигурационные профили аккаунтов, а не разные варианты команд.

## Виды catch-up

| Вид | Что собирается | Период и scope | Выход |
| --- | --- | --- | --- |
| Daily catch-up | Только исходящие/self-сообщения владельца | Автоматически после последнего daily-отчёта до вчера | `reports/daily/YYYY-MM-DD.md` |
| Catch-up одного чата или группы | Полная история всех участников выбранного чата | Чат и обе границы периода должны быть названы явно | Отдельная именованная папка, Markdown по дням, индекс медиа и raw-слой |
| Full-account catch-up за период | Все сообщения доступных диалогов, попавшие в период | Обе даты и аккаунт должны быть названы явно | Отдельная именованная папка, Markdown по дням, индекс медиа и raw-слой |

Примеры второго и третьего вида — выгрузка группы Haru и поездочный catch-up по Шанхаю. Это специальные read-only экспорты. На текущем CLI они не являются режимами `daily-catchup`: перед выполнением нужно проверить существующие команды и код, составить явный план выгрузки и не выдавать разовый скрипт за поддерживаемую публичную команду.

Если пользователь говорит только «сделай catch-up», выполняется первый вид. Расширять scope до всех участников, конкретной группы или всего аккаунта можно только по явному запросу.

## Содержимое отчёта

Markdown предназначен для чтения человеком или передачи другому агенту. В нём нужны:

- дата, время, чат и автор там, где автор важен для выбранного вида catch-up;
- текст сообщения с сохранением последовательности сообщений;
- рабочая Markdown-ссылка на Telegram-сообщение, когда её можно построить;
- компактное обозначение вложения;
- расшифровка речи непосредственно рядом с соответствующим voice/audio/video;
- текстовое описание или OCR изображения, только если пользователь явно заказал vision-разбор.

В Markdown не выводятся технические пути, байты, cache keys, ffmpeg/Vosk stderr, внутренние поля JSONL, повторяющиеся счётчики сканирования и пустые разделы. Последовательности `\\n`/`<br>` в тексте отображаются обычными абзацами или переносами.

Raw JSONL сохраняет source metadata, идентификаторы, локальные пути, статусы скачивания, ASR-события и ошибки, необходимые для аудита и повторной сборки. Пользователю по умолчанию передаётся папка с Markdown, а не JSONL.

## Медиа и транскрибация

Для daily catch-up действуют штатные правила:

- voice, audio и round video транскрибируются, если ASR настроен;
- обычные video по умолчанию проходят только в режиме `phone`: вертикальное телефонное видео, не длиннее 6 минут, не больше 80 MiB на preflight и не выше 1080x1920;
- горизонтальные, слишком длинные и слишком большие generic video не отправляются в ASR;
- модель Vosk загружается один раз на весь catch-up-прогон и переиспользуется между днями;
- кэш привязан к Telegram media id, поэтому одно и то же медиа не должно повторно скачиваться и распознаваться;
- временные audio/video удаляются после обработки; пользовательские изображения и документы сохраняются только когда этого требует вид экспорта;
- ASR/ffmpeg ошибки остаются в машинном логе и не подмешиваются в текст расшифровки.

Транскрибация аудиодорожки и анализ изображения — разные операции. Vosk не описывает скриншоты и кадры. Для полного визуального разбора нужен отдельный vision/OCR-проход, после которого текстовые описания добавляются рядом с медиа; сами изображения можно удалить только после проверки полноты описаний и если пользователь это разрешил.

## Порядок выполнения

1. Проверить `git status`, авторизацию нужного профиля через `doctor`, последнюю дату отчёта и свободное место.
2. Для обычного запроса запустить `make daily-catchup PROFILE=main PROGRESS=1` без ручной начальной даты.
3. Для специального catch-up сначала зафиксировать аккаунт, scope, обе даты, необходимость всех участников, типы медиа, ASR и vision/OCR.
4. Не запускать второй ASR/catch-up процесс, если первый ещё работает.
5. Дождаться завершения процесса; не оставлять фоновую сессию без контроля.
6. Проверить созданные даты, `complete=true`, наличие Markdown и отсутствие технических ошибок в человекочитаемом тексте.
7. Проверить ASR-статистику: cache/transcribed/skip/error, нулевые временные файлы и отсутствие зависшего helper-процесса.
8. Удалить только временные файлы текущего прогона. Не удалять отчёты, raw-слой или кэш без явной причины.

## Критерий готовности

Catch-up готов, когда покрыт весь запрошенный диапазон, сегодняшний день исключён для автоматического daily catch-up, каждый новый день атомарно опубликован, подходящие голосовые имеют расшифровку либо явный машинный статус причины пропуска, Markdown не содержит runtime-шума, временные файлы очищены, а процесс завершён.

В финальном ответе нужно назвать фактически созданный диапазон, число новых отчётов, путь к пользовательской папке, итог ASR/ошибок и любые реальные пропуски. Нельзя сообщать об успехе только на основании запуска команды.
