# Catch-up в Telegram Harvest

Этот файл — канонический контекст для запросов «сделай catch-up» или «сделай катчап». Перед таким прогоном агент должен прочитать его и не восстанавливать смысл команды по старым чатам.

## Catch-up без уточнений

По умолчанию catch-up означает **daily catch-up основного личного аккаунта**:

- профиль: `main`;
- данные: исходящие/self-сообщения владельца аккаунта во всех доступных диалогах плюс явно настроенные дополнительные отправители в конкретных чатах;
- текущий дополнительный источник: бот Trackmate в группе Haru;
- период: день после самого свежего `reports/daily/YYYY-MM-DD.md` по вчерашний день включительно;
- сегодняшний незавершённый день не входит;
- существующие отчёты не переписываются;
- результат для человека: отдельный Markdown за каждый день в `reports/daily`;
- после успешного прогона весь диапазон последнего catch-up объединяется в `reports/daily/00-latest-catchup.md`;
- JSONL, ASR-логи, кэши и временные данные остаются в `.state/daily` и не являются пользовательскими отчётами.

Штатная команда:

```bash
make daily-catchup PROFILE=main PROGRESS=1
```

Если предыдущих daily-отчётов нет, начальная дата должна быть задана явно:

```bash
make daily-catchup PROFILE=main FROM=2026-07-01 PROGRESS=1
```

Нельзя выбирать профиль неявно. `main` и `study` — конфигурационные профили аккаунтов, а не разные варианты команд.

`daily` и `daily-catchup` — единственный пользовательский catch-up flow. `dump` и `sync` остаются низкоуровневыми read-only кирпичами для агентов и обслуживания данных; из них не нужно собирать отдельные full-chat/full-account catch-up форматы.

Дополнительные daily-источники задаются один раз как пары `chat_id:sender_id`:

```dotenv
TG_HARVEST_DAILY_ADDITIONAL_SENDERS=3740223926:8718303786
```

Для каждого затронутого диалога daily читает `messages.getHistory`, а затем локально оставляет self и настроенных дополнительных отправителей. Остальные участники Haru и других чатов в отчёт не попадают; `messages.search` не используется как источник полноты.

## Содержимое отчёта

Markdown предназначен для чтения человеком или передачи другому агенту. В нём нужны:

- дата, время, чат и автор там, где автор важен для выбранного вида catch-up;
- текст сообщения с сохранением последовательности сообщений;
- рабочая Markdown-ссылка на Telegram-сообщение, когда её можно построить;
- явная отметка `Переслано из`/`Переслано от` для форвардов, с раскрытым Telegram источником и ссылкой на оригинальный пост, когда эти данные доступны;
- компактное обозначение вложения;
- расшифровка речи непосредственно рядом с соответствующим voice/audio/video;
- текстовое описание или OCR изображения, только если пользователь явно заказал vision-разбор.

В Markdown не выводятся технические пути, байты, cache keys, ffmpeg/Whisper stderr, внутренние поля JSONL, повторяющиеся счётчики сканирования и пустые разделы. Последовательности `\\n`/`<br>` в тексте отображаются обычными абзацами или переносами.

Raw JSONL сохраняет source metadata, включая структурированный `forward` из Telegram `fwd_from`, идентификаторы, локальные пути, статусы скачивания, ASR-события и ошибки, необходимые для аудита и повторной сборки. Пользователю по умолчанию передаются дневные Markdown-файлы, а не JSONL.

ZIP-архивы по умолчанию не создаются. В финальном ответе нужно дать ссылки на готовые папки и Markdown-файлы; упаковывать результаты следует только по явному запросу пользователя.

`00-latest-catchup.md` — основной файл для передачи в другой чат. Он является производным представлением: собирается атомарно из дневных Markdown только после завершения всех дней, не заменяет их и не влияет на вычисление следующей даты catch-up.

## Медиа и транскрибация

Для daily catch-up действуют штатные правила:

- voice, audio и round video транскрибируются, если ASR настроен;
- обычные video по умолчанию проходят только в режиме `phone`: вертикальное телефонное видео, не длиннее 6 минут, не больше 80 MiB на preflight и не выше 1080x1920;
- горизонтальные, слишком длинные и слишком большие generic video не отправляются в ASR;
- bounded ASR pipeline использует один production Whisper large-v3-turbo q5_0 Metal worker; модель загружается один раз при первой ASR job и переиспользуется между днями;
- кэш привязан к Telegram media id и runtime/model/decode/gate config, поэтому одно и то же медиа переиспользуется только при той же транскрипционной конфигурации;
- Telegram scan и выбор следующего файла остаются у единственного последовательного producer; downloader распределяет два глобальных chunk slots между двумя файлами до 1 MiB либо одним файлом от 1 MiB, а history RPC не пересекается с download wave;
- producer может скачать следующее медиа параллельно локальному `ffmpeg → speech gate → Whisper`, а collector применяет результаты перед публикацией в детерминированном порядке;
- временные audio/video удаляются после обработки; пользовательские изображения и документы сохраняются только когда этого требует вид экспорта;
- ASR/ffmpeg ошибки остаются в машинном логе и не подмешиваются в текст расшифровки.

Транскрибация аудиодорожки и анализ изображения — разные операции. ASR не описывает скриншоты и кадры. Для полного визуального разбора нужен отдельный vision/OCR-проход, после которого текстовые описания добавляются рядом с медиа; сами изображения можно удалить только после проверки полноты описаний и если пользователь это разрешил.

## Порядок выполнения

1. Проверить `git status`, авторизацию нужного профиля через `doctor`, последнюю дату отчёта и свободное место.
2. Для обычного запроса запустить `make daily-catchup PROFILE=main PROGRESS=1` без ручной начальной даты. Команда должна выполнить один Telegram range-scan всего нового диапазона и только затем разбить записи по дневным отчётам; отдельный полный scan для каждого дня не допускается. В непрерывном автоматическом запуске неизменившиеся dialog могут быть доказанно пропущены по checkpoint. Ручной `FROM`, исторический диапазон и любой checkpoint mismatch обязаны идти через полный fallback.
3. Не запускать второй ASR/catch-up процесс, если первый ещё работает.
4. Дождаться завершения процесса; не оставлять фоновую сессию без контроля.
5. Проверить созданные даты, `complete=true`, дневные Markdown, `00-latest-catchup.md` и отсутствие технических ошибок в человекочитаемом тексте.
6. Проверить, что настроенные дополнительные отправители представлены в релевантных днях, но сообщения остальных участников их чатов не попали в daily.
7. Проверить ASR-статистику: cache/transcribed/skip/error, нулевые временные файлы и отсутствие зависшего helper-процесса.
8. Проверить строку `timings` и сохраненный `.state/daily/timings/*.json`: в нем всегда есть Telegram scan, download, download transport bytes/throughput/thread decisions/retries/floods, ffmpeg, model cold-start, ASR, render, stage work, audio seconds, ASR/pipeline speed, backend/model/accelerator, media pipeline span/overlap/workers/queue/resources, static RPC spacing/calls/wait/floods, history data/empty/sparse/proof counters и dialog checkpoint counters/fallback.
9. Для успешного автоматического catch-up проверить `.state/daily/dialog-checkpoint.json`: `account_id`, `scope_fingerprint`, `verified_through`, `complete=true`, `top_message_id`, `verified_message_id` и `head_fully_verified`. `verified_message_id` может продвигаться входящим raw-сообщением, не попавшим в отчет, но только если оно реально прочитано, находится строго до exclusive end и весь dialog scan завершен. Head из следующего, ещё не опубликованного дня не должен иметь `head_fully_verified=true`. `updated_at` не должен меняться после incomplete/error run или ошибки merged publish.
10. Удалить только временные файлы текущего прогона. Не удалять отчёты, raw-слой, timing reports, dialog checkpoint или кэш без явной причины.

## Критерий готовности

Catch-up готов, когда покрыт весь запрошенный диапазон, сегодняшний день исключён для автоматического daily catch-up, каждый новый день атомарно опубликован, `00-latest-catchup.md` содержит весь диапазон последнего прогона, подходящие голосовые имеют расшифровку либо явный машинный статус причины пропуска, сохранен отдельный timing report, Markdown не содержит runtime-шума, временные файлы очищены, а процесс завершён.

В финальном ответе нужно назвать фактически созданный диапазон, число новых отчётов, дать ссылку на `00-latest-catchup.md`, указать итог ASR/ошибок и любые реальные пропуски. Нельзя сообщать об успехе только на основании запуска команды.
