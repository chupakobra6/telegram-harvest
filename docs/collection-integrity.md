# Полнота сбора

## Диапазон и нагрузка — разные ограничения

`sync` читает все новые сообщения после подтверждённой позиции. Общего `--limit` у него нет. `dump --all`, full backfill и account-sync не имеют общего лимита сообщений. Обычный `dump --limit N` — намеренная выборка: её вывод содержит `complete=false`, если граница истории не доказана. Размер одной history-страницы остаётся 100, пауза RPC — 500 мс, download budget — два chunk slots. `FLOOD_WAIT` соблюдается с ограниченным числом повторов; прерывание возвращает ошибку.

Короткая страница истории, диалогов или топиков не доказывает полноту. Обход продолжается до подтверждённой границы либо пустой страницы; неповторяющаяся позиция проверяется. Неполная или непригодная для продолжения выдача — ошибка, а не отсутствие данных.

Daily/catch-up по умолчанию перечисляет все доступные обычные и архивные диалоги, сохраняя прежний фильтр self/разрешённых дополнительных отправителей. Общего `--limit` у архивного daily нет: раньше он обрезал уже собранные записи перед публикацией и мог оставить полный checkpoint при неполном отчёте. Явный диагностический `--dialog-limit` делает результат неполным, если диалоги остались за границей; такой проход не подтверждает полный checkpoint. Для намеренной короткой выборки используются `dump` или `compact`.

## Сохранение и восстановление

Догрузка новых сообщений в `sync` и `account-sync` использует один механизм: страницы сохраняются в приватный `.incremental.jsonl`, а размер сохранённых данных и следующая позиция — в fsync-журнал рядом со state. После отмены следующий запуск продолжает с сохранённой страницы; обычный `sync` также возобновляет начатую сверку старых сообщений. Незафиксированный хвост временного файла отбрасывается и перечитывается. До завершения диапазона рабочие JSONL остаются прежними. Если отменено чтение, после освобождения блокировки из них можно строить представления.

После полного чтения журнал фиксирует размеры выходных файлов. К ним дописывается собранная часть, файлы синхронизируются, затем атомарно сохраняется state. Повтор после частичной публикации проверяет уже записанные байты и дописывает остаток без дублей; неожиданные данные другого писателя вызывают ошибку. Журнал привязан к чату, теме, диапазону и выходам, поэтому смена назначения не перенаправляет восстановление в другой файл.

На время публикации синхронизация сохраняет рядом с каждым выходным JSONL `*.harvest-pending` с каноническим путём владельца state. Если процесс оборвался до завершения публикации, `compact` и `agent-view` возвращают понятную ошибку вместо чтения незавершённого исходника. Возобнови соответствующий `sync` или `account-sync`: он восстановит запись и удалит маркер. Файлы незавершённой загрузки сохраняй до этого восстановления.

`sync --all --reset` остаётся явным началом полного backfill; `sync --all` продолжает его. Неполный результат не выдаётся за завершение. Существующий архив не сбрасывается при обычном восстановлении.

У `account-sync` полный backfill также возобновляется. Существующий `.incremental-pending.json` восстанавливается и удаляется перед переходом на общий механизм догрузки; новые загрузки его не создают. Проверка числового ID аккаунта и раздельные каталоги `<тип>-<id>` сохраняют принадлежность архива.

## Владение общими файлами

MTProto-команды удерживают блокировку сессии до завершения работы. Файл `*.runtime.lock` остаётся на месте после освобождения: следующий процесс захватывает тот же объект. Наличие файла само по себе не означает занятость.

`sync`, `compact`, `agent-view`, `dump` и дневные отчёты дополнительно захватывают используемые входы и выходы по каноническим путям через `*.harvest.lock`. Одинаковые пути, включая пути через символьные ссылки и из разных профилей, разделяют одного владельца. `account-sync` также удерживает весь каталог архива, а публикация catch-up — дневные входы, общую сводку и checkpoint. Блокировки освобождаются после работы и закрытия файлов; при занятом ресурсе команда возвращает ошибку до его изменения. Операции с непересекающимися ресурсами остаются независимыми. Служебные файлы блокировок сохраняются, чтобы не разделить владение между старым и вновь созданным файлом.

Для `compact` выбирай выходной файл, отличный от исходного JSONL; для `agent-view` — отдельный каталог, не содержащий исходник. Проверка сравнивает фактические пути после разрешения символьных ссылок. Пересборка через ссылку меняет целевой каталог и сохраняет саму ссылку.

## Правки уже полученных сообщений

Новый ID и изменение старого сообщения — разные сигналы. Для заданного периода:

```bash
bin/telegram-harvest --profile study sync --chat <chat> --name <stream> \
  --refresh-from 2026-09-01 --merged-out messages.jsonl --download-media
```

Проход читает весь период без лимита записей, добавляет отсутствующие сообщения и смысловые изменения, не повторяя неизменившиеся. Метаданные unread/head/views/cache не считаются изменением учебного текста. Версия хранится в append-only JSONL с `revision`; старые версии не удаляются. Agent-view при ревизии пересобирается с последней версией каждого ID; compact также исключает устаревшие версии. Время редактирования сохраняется, если его прислал Telegram.

Обычный ID-sync сам по себе не обещает обнаружить правку произвольно старого сообщения. Период регулярной сверки задаёт вызывающий проект. Удаления и сообщения, к которым Telegram уже не даёт доступа, не восстанавливаются из отсутствия ID.

## Регрессии

Локальные проверки охватывают 250/6000 новых сообщений при прежнем cap 100, отмену после fsync страницы с частично записанной следующей, частичную публикацию и повтор без дублей, новый head во время продолжения, короткую/повторную страницу, ограниченный preview, 601 диалог, правку старого текста и пропущенный старый ID, повтор сверки без дельты и отсутствие старой версии в представлениях. Владение проверяется передачей блокировки между тремя процессами, совпадающими и независимыми выходами, включая отказ чтения незавершённой публикации.

Перед выпуском выполняй `make verify`. Живую проверку действующего бинарника добавляй для изменений Telegram-взаимодействия и только в разрешённом сценарии; локальные изменения блокировок и восстановления проверяются на временных данных и подставном источнике. Успех этих проверок не доказывает полноту всей прошлой истории.
